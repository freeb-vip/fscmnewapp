# App 扫码采购入库与离线恢复

完成库位批次后，App 在同一 Room 事务保存批次范围、扫描原始数据和自动采购意图。草稿取消不触发采购；旧批次只有明确补交后才创建意图。

1. 库位与箱唛先上传，由后端返回持久化 `scan_ack`。重复扫描、库位更正也返回凭据；旧响应可通过 `POST receiving-sessions/:id/inbound-scan-acks/resolve` 恢复。
2. “采用后台库位”保留待联网确认状态，通过 `POST receiving-sessions/:id/inbound-items/:box_plan_id/accept-location` 复核库位。该操作属于扫码同步，旧批次也可以处理，不会因此补交采购。
3. 已确认的箱唛按来源批次、实际会话分组，持久化完整请求及固定请求 ID，再调用 `POST receiving-purchases/sessions/:id/auto-receipts`。其余箱唛恢复上传后另行提交新增范围。
4. 请求响应丢失时重放原请求，已获得任务 ID 后只查询原任务。所有相关请求在发送时核对账号和工作空间，使用同一会话快照的认证信息。
5. 后端任务独立执行。只有平台确认成功的箱唛/SKU 事实计入已入库；结果未知保持未入库并禁止重新发送。

采购未关联或可收明细未全部就绪时，已提交批次进入 `waiting_purchase`，由后端每30秒检查并在就绪后继续原任务。App只查询原任务，退出或断网不影响后台恢复。采购卡片显示等待原因和“将自动继续”，等待不计失败，也不显示失败重试按钮；任务结果和批次记录提供 `waiting_reason.code/message`。库位或数量等其他业务失败仍需处理后显式重试。只有后端已接收的采购批次进入此流程，单独上传扫描不会自动补交采购。

后端135迁移会筛选并核查此前仅因采购未关联／未就绪失败的原自动批次；原请求、扫描范围及防重事实保留。需先发布后端及迁移，再更新网页和App。

## 数据迁移

Room 16→17 增加 `auto_receipt_scan_items`。迁移只为已有自动意图保存原扫描数据，原自动提交请求及旧手动采购数据保留。找不到原记录时保留显式错误，联网尝试恢复凭据，无法恢复则需要核实，不能静默跳过。

活动扫码记录因重新扫描被替换或删除时，已完成批次的独立快照不受影响。扫描上传结果与快照更新在同一事务中提交。

## 页面

- “同步状态”下方区分扫码同步与采购入库，显示最近三条记录。
- 详情按产品展示应入库、已入库、未入库和其中失败数量；混箱按 SKU 成功事实计量，整箱全部成功才计为完成箱。
- 入库记录的当前数量来自收货事实；“尝试记录”分页查看不可变历史事件，包括共享原任务的执行记录。
- 失败重试会展示原任务及影响箱数；未知结果只能查看核实信息。
- 网络恢复自动加载，有活动任务每五秒查询；离开页面或结束后停止，离线显示缓存及时间。

## 上线顺序

先上线 FSCM 后端兼容接口和迁移 132，再安装新版 App。迁移不触发历史采购收货。不清除 Room 数据进行回退；回退 App 前应保留数据库备份和未完成请求。

开发验证与文件清单见 FSCM `docs/features/receiving-purchase-integration.md` 的“扫码恢复修复”部分。真实采购单、平台库存和设备离线扫码仍需使用指定测试采购单现场验收。
